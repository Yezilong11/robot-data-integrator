# 问题集构建策略

> 版本：3.0
> 编制日期：2026-08-12
> 适用范围：v3 系统验证

---

## 1. 目标

建立问题集（固定 JSON 模板）→ 手动执行并记录（结构化 JSON + 截图）→ 产出两个文件夹（问题集、执行记录），供后续统计分析。

## 2. 两层测试架构

| 层级 | 内容 | 占比 |
|---|---|---|
| **单源测试（主导）** | 针对单个数据源逐个测，验证检索/下载/格式/真实度 | 约 70% |
| **多源混合测试** | 用真实目标组合多个源，验证端到端工作流 | 约 30% |

## 3. 工程化交付结构（两个文件夹）

```
问题集构建策略.md
├── problem_set/                 # 文件夹一：问题集（测试前定稿）
│   └── problem_set.json         #   问题集清单，固定 JSON 模板（见 §4）
└── records/                     # 文件夹二：执行记录（测试中产生）
    └── <case_id>/               #   每道题一个文件夹
        ├── record.json          #   结构化执行记录（固定模板，见 §5）
        └── screenshots/         #   截图（文字记录 + 图片证据）
            ├── 01_parse_goal.png
            ├── 02_retrieve.png
            └── 03_package.png
```

> 最终交付 = `problem_set/` + `records/` 两个文件夹；统计与报告基于记录数据生成，不再是主交付物。

## 4. 问题集格式（固定 JSON 模板）

`problem_set/problem_set.json` 为唯一问题集载体，所有题目按同一 schema 定义，禁止改结构。

### 4.1 模板定义

```json
{
  "schema_version": "1.0",
  "meta": {
    "name": "v3 问题集",
    "created_at": "2026-08-12",
    "architecture": {
      "single_source": { "ratio": 0.7, "note": "单源测试（主导）" },
      "multi_source": { "ratio": 0.3, "note": "多源混合测试" }
    }
  },
  "problems": [
    {
      "case_id": "ss_arxiv_001",
      "layer": "single_source",
      "category": "paper",
      "source": ["arxiv"],
      "target": "检索 robot grasping 的论文",
      "lang": "EN",
      "expected": {
        "req_types": ["PAPER"],
        "quality": ["real", "fallback"],
        "format": ["xml"],
        "min_files": 1
      },
      "priority": "P0"
    }
  ]
}
```

### 4.2 字段说明

| 字段 | 取值 | 说明 |
|---|---|---|
| `case_id` | 字符串 | 唯一编号：单源 `ss_<源>_<序号>`，多源 `ms_<序号>` |
| `layer` | `single_source` / `multi_source` | 所属层级 |
| `category` | paper/code/dataset/robot_urdf/mesh/grasp/sim_config/policy/sensor/end_to_end | 数据类型 |
| `source` | `DataSource` 值列表 | 被测源（单源 1 个，多源可多个） |
| `target` | 字符串 | 前端实际输入的问题原文 |
| `lang` | ZH / EN / MIX | 语言 |
| `expected.req_types` | `DataReqType` 列表 | 期望产出的需求类型 |
| `expected.quality` | real/fallback/unknown/synthetic | 允许的 `data_source_quality` |
| `expected.format` | 字符串列表 | 期望文件格式 |
| `expected.min_files` | 整数 | 数据包最少文件数 |
| `priority` | P0 / P1 / P2 | 优先级 |

### 4.3 单源问题示例（数据源分组）

| category | source | 代表 target |
|---|---|---|
| paper | arxiv / ieee / paperswithcode | 检索 "robot grasping" 的论文 |
| code | github / paperswithcode | 检索 Franka 抓取开源仓库 |
| dataset | github / huggingface / zenodo / graspnet | 检索 YCB 抓取数据集 |
| robot_urdf | franka / robotiq / allegro | 获取 Panda URDF |
| mesh | ycb / google_scanned / github | 获取 YCB 香蕉 mesh |
| grasp | graspnet / dexgrasp / ycb | 获取 banana 的单个 grasp 文件 |
| sim_config | mujoco / isaac | 命中 mujoco_menagerie 真实场景 |
| policy | huggingface / github | 检索抓取策略权重 |
| sensor | github / zenodo | 检索机械臂关节数据 |

### 4.4 多源问题示例

| case_id | target | source 组合 |
|---|---|---|
| ms_001 | Franka Panda grasps YCB banana in MuJoCo | franka + ycb + mujoco |
| ms_002 | 我想在 MuJoCo 里用 Franka Panda 机器人抓取 YCB 香蕉 | franka + ycb + mujoco |
| ms_003 | Kinova Gen3 picks up EGAD mug in Isaac Sim | kinova + egad + isaac |
| ms_004 | UR5 with Robotiq 2F-85 grasps YCB apple | ur5 + robotiq + ycb |
| ms_005 | Franka Panda stacks YCB blocks in PyBullet | franka + ycb + pybullet |
| ms_006 | 用 Franka 在 MuJoCo 里抓取香蕉（无 YCB 关键词） | 解析鲁棒性 |
| ms_007 | 抓取 YCB 香蕉（未指定仿真器） | 缺省场景处理 |
| ms_008 | 只要 Franka Panda 的 URDF | 单需求路径 |

## 5. 执行记录格式

### 5.1 目录结构

每道题在 `records/<case_id>/` 下生成一份 `record.json` + `screenshots/` 截图。

### 5.2 record.json 模板

```json
{
  "schema_version": "1.0",
  "case_id": "ss_arxiv_001",
  "input": "检索 robot grasping 的论文",
  "executor": "B",
  "executed_at": "2026-08-12T14:30:00+08:00",
  "env": {
    "llm_model": "qwen-plus",
    "llm_base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
    "mode": "real",
    "review_decision": "satisfied"
  },
  "observations": {
    "parse_goal": {
      "req_list": ["PAPER"],
      "vs_expected": "match"
    },
    "retrieve": [
      {
        "req_id": "req_000",
        "source": "arxiv",
        "quality": "real",
        "error": null
      }
    ],
    "validate": { "errors": 0, "warnings": 0, "runtime_check": "passed" },
    "package": {
      "dir": "data/output_packages/package-20260812-143000",
      "status": "complete",
      "file_count": 2
    }
  },
  "screenshots": [
    { "file": "screenshots/01_parse_goal.png", "desc": "目标解析阶段界面" },
    { "file": "screenshots/02_package.png", "desc": "数据包结果页" }
  ],
  "verdict": "PASS",
  "failure_category": null,
  "failure_reason": null,
  "notes": ""
}
```

### 5.3 输入问题存储

- 输入的问题原文存于 `record.json` 的 `input` 字段——执行时**实际输入**前端的问题，可与问题集 `problem_set.json` 中该 case 的 `target` 不同（执行中临时改措辞），判定与统计以 `input` 为准。
- `problem_set.json` 的 `target` 是**设计时**问题，`record.json` 的 `input` 是**执行时**问题，两者对应关系由 `case_id` 关联。

### 5.4 截图规范

- 每道题至少 2 张：**运行中阶段截图** + **数据包结果截图**；FAIL 必须截**报错信息**。
- 命名：`NN_<stage>.png`（01_parse_goal、02_retrieve、03_validate、04_package、05_error）。
- 内容：前端界面截图（含输入的目标、review 决策、产物路径），保证可复现取证。

### 5.5 判定与失败原因（保留）

**判定三档**：

| 值 | 条件 |
|---|---|
| PASS | 数据包完整、无 ERROR、文件可加载 |
| PASS_WITH_FALLBACK | 包可用但有显式降级（manifest 有 `is_fallback`/`missing_items` 记录） |
| FAIL | 无数据包 / 崩溃 / 含 ERROR / 产出内容错误 |

> 降级不算失败，但必须显式可追溯；无标记的静默降级记为 FAIL。

**失败原因分类码**：

| 码 | 含义 |
|---|---|
| P1_PARSE | LLM 目标解析失败（req 类型错/漏/UNKNOWN） |
| P2_RETRIEVE | 检索失败（无结果/timeout/rate_limit） |
| P3_SOURCE | 数据源不可用（404/401/tar 无法单文件获取） |
| P4_FORMAT | 格式不兼容（xacro/glb/python 场景） |
| P5_RUNTIME | 运行时验证失败（MuJoCo 加载/mesh 缺面） |
| P6_FRONTEND | 前端/流程问题（interrupt 卡死/resume 失败） |
| P7_ENV | 环境问题（Key 缺失/依赖缺失/网络） |
| P8_OTHER | 其他（产出内容错误等） |

## 6. 分工（A、C、D、E、F 五人）

> 五人职责均围绕两大产出：**问题集**（`problem_set/problem_set.json`，定义测什么）与 **结果集**（`records/`，记录测出来什么）。支持性工作（环境准备、操作手册）最终只为产出这两份交付物服务，不成为独立目标。

### 6.1 A — 组长 / 架构师

1. 定验收线：明确 P0 题通过标准与问题集规模（见 §2/§4）。
2. 主持问题集评审：组织全员评审 `problem_set/problem_set.json`，逐题确认题目、期望输出与判定口径无歧义。
3. 裁定判定边界：对存疑结果（如"降级是否显式"）做最终裁定，保证结果集记录口径一致。
4. 主持复盘会：依据结果集分析 FAIL / PASS_WITH_FALLBACK 根因，输出问题集/结果集的改进建议。
5. 终审交付：验收 `problem_set/` + `records/` 两个文件夹是否完整、达标。

### 6.2 C — 数据工程师

1. 设计数据源类题目：paper/code/dataset/grasp/sim_config/policy/sensor 类 case 写入 `problem_set.json`，含期望 `quality`/`format`。
2. 执行单源题：认领并执行数据源相关 case，填写 `record.json` + 截图。
3. 分析检索与数据源失败：P2_RETRIEVE / P3_SOURCE 根因定位到具体 adapter（404/401/timeout/限流/tar 无法单文件获取）。
4. 跑探活：执行 `uv run python scripts/_probe_adapters.py`，记录 15 源 construct/search/fetch 可用性。
5. 核验真实度：对照 manifest 检查 `data_source_quality`（real/fallback/synthetic）是否与实际产物一致。

### 6.3 D — 机器人工程师

1. 设计格式/仿真类题目：robot_urdf/mesh/sim_config 类 case 写入 `problem_set.json`。
2. 执行格式/仿真类单源题及多源题，填写 `record.json` + 截图。
3. 数据包可加载性验证：URDF 用 `yourdfpy`（`load_meshes=True`）、Mesh 用 `trimesh`、MJCF 用 `mujoco.mj_step` 逐类验证。
4. 分析 P4_FORMAT / P5_RUNTIME 失败：定位格式不兼容（xacro/glb/python 场景）与运行验证失败根因。
5. 核验数据包结构：确认 `robots/objects/grasps/sim_config/` 目录与 `manifest.json` 记录一致。

### 6.4 E — 产品工程师

1. 写前端操作手册：真实流程操作步骤（模式选择 → 输入目标 → 观察阶段 → human_review 中断 → 提交决策 resume）。
2. 执行环境保障：`.env` 配置、依赖安装（`uv sync --extra runtime`）、前端启动与问题排查。
3. 截图取证规范执行：确认每 case 截图符合规范（阶段截图 + 结果截图，FAIL 必截报错）。
4. 执行流程类 case（多源端到端为主），记录并分析 P6_FRONTEND（interrupt 卡死/resume 失败/UI 异常）。
5. 汇总执行环境信息：收集各 case 的 LLM 模型与配置，供统计按模型分桶。

### 6.5 F — 质量工程师

1. 维护问题集 JSON：管理 `problem_set/problem_set.json` 版本与题目增删。
2. 建立记录模板：维护 `records/<case_id>/record.json` 模板与 `screenshots/` 目录规范。
3. 校验记录质量：JSON 格式合法、字段完整率 ≥90%、判定与失败分类码填写一致。
4. 维护执行进度表：case × 执行人 × 状态（未执行/已执行/已判定/已复核），每日同步。
5. 汇总统计：通过率/降级率/失败率、分维度（语言/源/需求类型）统计、失败原因 TOP 3。
6. 产出整理：汇总 `problem_set/` + `records/` 两个文件夹交付，按需生成统计摘要。

> 执行分配：单源题按专长认领（C 主测数据源类、D 主测格式/仿真类、E 主测流程类），多源 8 题全员交叉各测一轮；每 case 的输入问题原文必须写入 `record.json` 的 `input` 字段。

## 7. 流程

1. **定稿**：问题集 JSON 定稿（组长评审通过）→ 入库 `problem_set/problem_set.json`。
2. **执行**：按认领 case 手动执行（前端真实流程，见 §4/§5），每 case 完成 `record.json` + 截图。
3. **汇总**：质量工程师校验 JSON 格式、核对判定一致性，输出统计表。
4. **产出**：交付 `problem_set/` + `records/` 两个文件夹；按需生成统计摘要。
