# Day 3：执行中段与多源交叉

## 当日目标

完成剩余单源题（约 2/3），多源交叉测试启动：每人对之前未测的多源题再测 1 轮，暴露 LLM 随机性与执行差异。

## 各角色详细工作

### A（组长/架构师）

1. 执行多源题第二轮（与 Day 2 不同的题，如 `ms_003` Kinova/Isaac）。
2. 裁定 Day 2 遗留的全部存疑 case。
3. 观察同一题两人执行的结果差异，判断是否属系统随机性，必要时定"结果以 X 为准"的口径。

### C（数据工程师）

1. 完成剩余数据源类单源题（zenodo / graspnet / dexgrasp / ieee 等），继续按专长执行。
2. 交叉测多源题 1 道（与首测不同的题，如 `ms_004` UR5/Robotiq），记录差异。
3. 汇总首两天数据源类 FAIL 的根因初判（指向具体 adapter）。

### D（机器人工程师）

1. 完成剩余格式/仿真类单源题（allegro/robotiq/google_scanned 等）。
2. 交叉测多源题 1 道（如 `ms_005` PyBullet 堆叠）。
3. 对 sim_config 类记录逐一确认 `runtime_check`（mj_step 通过/失败）与 fallback 标记。

### E（产品工程师）

1. 完成流程类剩余 case，重点处理前端异常（P6_FRONTEND）。
2. 交叉测多源题 1 道（如 `ms_006` 无 YCB 关键词）。
3. 收集各执行人反馈，更新操作手册第二版（含踩坑记录）。

### F（质量工程师）

1. 校验当日记录质量，标记缺失字段/缺截图/判定空白的 case 要求补。
2. 更新进度表：标出"未执行/已执行/已判定/已复核"。
3. 统计已判定 case 的判定分布，识别口径漂移 case 上报 A 裁定。

## 与 A 的对接点

| 对接人 | 对接内容 | 期望输出 |
|---|---|---|
| C/D/E | 交叉测试的差异结果 | A 判断是否系统性问题 |
| F | 口径漂移 case 清单 | A 统一裁定口径 |
| 全员 | 当日完成情况 | F 晚间同步进度 |

## 当日出口标准

- [ ] 单源题累计完成约 2/3
- [ ] 每人完成至少 1 道交叉多源题
- [ ] 无未裁定的存疑 case 过夜
