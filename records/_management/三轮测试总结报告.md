## 三、关键发现

1. **引用=完整交付后，成功率反映真实交付**。大文件超限又给 URL + wget 指引 + explain 说明的 24 题计 PASS；
   只有 16 题是真未交付（候选源全败 / 疑似占位 / 语义错配 / 候选零重叠）。
2. **没有无声降级**。引用交付必须带 file_url + download_guide + explain；缺 URL/指引由
   `download_integrity` ERROR 兜底判 FAIL（assemble 锚点，未放行任何"裸引用"）。
3. **真实网络下源侧可得性是主要瓶颈**（16 个真失败）：
   候选源双向失败 8（github format_mismatch / huggingface unknown）、疑似占位 6、语义错配 3、零重叠 1。
   policy（5/5）与 sensor（7/7）全 FAIL——权重源与传感器数据源在真实网络上拿不到或返回占位。
4. **慢源需要充足预算，预算不足是误标而非真实失败**。dexgrasp 等源单题需 4–8 分钟，
   第一轮 300s 系统性误标 17 题超时；预算提到 2400s 后复核轮 17/17 全 PASS、零超时残留。
   该认知已同步到用户使用场景：`per_req_timeout` 180→1200s、判卷脚本 300→2400s、回查窗口 600→1800s，
   测试链路与用户前端链路预算一致。
5. **语义校验真实命中不误拦**。`ss_dataset_hf_002`（整改前 P3 语义错配案）真实命中正确数据后
   纯下载 PASS；错配拦截在 zenodo 传感器题（joint angles/force torque → 无关记录）如实生效。

## 五、结论与建议

- **结论**：整改目标达成。四类非几何数据交付链路在真实网络下可执行、可记录、可归因；
  引用交付形态按用户决策计为完整交付；真正未交付的 16 题全部如实 FAIL 并带下载指引；
  慢源不再因预算不足被误标，用户使用场景与测试同口径。
- **成功率的解读**：66.7% 反映"交付了可用的获取路径（落盘或引用+指引）"；
  33.3% 真失败主要是**源侧可得性**（权重/传感器源在真实网络拿不到或返回占位），方向在源侧排查与后续源补全。
- **后续建议**（人工验收项）：
  1. `backfill-errors --apply` 写回 18 条自动归因 + 32 条人工补正台账；
  2. 预算相关调整已完成闭环（脚本 2400s / `per_req_timeout` 1200s / 回查 1800s），无需再改；
  3. 判卷脚本 `scripts/replay_frontend_problem_set.py` 已按修订口径更新（引用=完整交付），`--only` 支持多 case。
