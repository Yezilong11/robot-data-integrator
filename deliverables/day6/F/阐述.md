# Day 6｜测试汇总阐述

## 这次交付是什么

本轮不是只跑几个机器人数据接口，而是把“用户提出机器人数据需求”这一完整链路做成了可审计测试：题目在 `problem_set/`，每道题的真实输入、每个阶段观察、最终判定和截图在 `records/`。最终对外的核心交付仍然是这两个文件夹；本目录的报告用于说明它们是否可信、有哪些边界，以及下一轮该怎么改。

本次正式题库是 63 题：55 道单源题验证一个数据源或一种格式能力，8 道多源题验证端到端组合。P0 共有 11 题，P0 的“可用”包括 PASS 和有明确降级证据的 PASS_WITH_FALLBACK。

## 最重要的结果

最终严格快照为 2026-08-19 14:43：63/63 已执行、判定、复核；PASS 14，PASS_WITH_FALLBACK 48，FAIL 1。严格 PASS 率是 22.22%，但本项目的核心可用率应看 PASS + 显式降级包，因此为 62/63，即 98.41%。P0 是 11/11 可用，超过 8/11 门槛；记录完整率、截图合规率均为 100%，记录校验没有 ERROR。

高降级率不等于测试失败。这里的 PWF 表示系统没有把不完整或替代数据伪装成成功，而是把“主源不可达、只拿到元数据、替代文件格式、外部数据源没有单文件”等事实写进了记录和数据包。这样的结果仍可供下游使用，但需要知道它不是原始最理想数据。

## 唯一失败意味着什么

唯一失败是 `ms_008`：用户只要 Franka Panda 的 URDF。系统的目标解析正确识别了要 URDF，却让 LLM 自行选择了 `allegro`、`robotiq`、`kinova` 三个候选源。这些 Adapter 都存在，但都没有 Franka Panda，因此连续 3 轮检索都没有结果，最后生成 0 文件的 failed 包，判为 `P2_RETRIEVE`。

这件事非常值得保留，而不是把它改成“系统没问题”：同一个输入通过脚本探针可以从 GitHub 兜底成功，说明失败不是数据彻底不存在，而是目标解析和候选源选择受 LLM 采样影响。真实前端没有静默换成成功结果，记录里保留了 5 张截图和错误证据，这正是问题集测试要捕获的系统边界。

因此下一轮最优先的修复不是再给 Franka Adapter 加数据，而是让厂商 URDF 的候选源受规则约束，例如 Franka 必须优先走 `franka -> github`。详见 [改进建议清单.md](改进建议清单.md)。

## 如何理解统计表

语言、数据源、需求类型的表都按“该 case 在题设中声明了什么”分组。多源题会同时计入多个 source 或 req_type，所以表中的 source 数量相加一定大于 63，这不是算错。C 的数据源可用性表则统计实际检索命中，它的“源”是运行时真正返回结果的 Adapter，和题设 source 的表不能直接对比。

同理，`quality=real` 和 `is_fallback=true` 不是同一概念：前者描述来源真实性，后者描述这次是否相对题设/主源走了降级。当前判定以 `verdict` 和明确的 fallback 证据为准，避免把跨源但真实的数据误当成未降级。

## 这次记录是否可信

F 对原始记录做了全量核查：63 个正式 case 目录都有 `record.json`，489 个截图引用都有对应图片，所有 case 至少 4 张截图，唯一 FAIL 有单独错误截图。运行 `.venv` 下的记录管理脚本后，题库只有 1 条非阻断 WARNING（注册的 Kinova 没有单源题），记录有 52 条已知 WARNING，没有 ERROR。

这些 WARNING 的主体是 28 条跨机器绝对路径：部分真实数据包留在各执行人的本机且不随仓库提交，因此本仓库能审计记录、manifest 证据和截图，但不能在当前机器直接重新加载所有包。这是本轮最大的可复现性缺口，下一轮应改为相对路径、内容哈希或可下载归档引用。

## 复核方法

在 Windows 仓库根目录运行以下命令即可复核结构和记录：

```powershell
.\.venv\Scripts\python.exe scripts\manage_test_records.py validate-problems
.\.venv\Scripts\python.exe scripts\manage_test_records.py validate-records
.\.venv\Scripts\python.exe scripts\manage_test_records.py all --strict
```

本机的 `uv run` 因 uv cache 目录状态无法初始化，所以本次使用项目 `.venv` 执行。严格统计的原始 case 明细在 [case_statistics.csv](case_statistics.csv)，最终数字和验收项在 [day6_statistics.md](day6_statistics.md)，交付范围在 [交付核对清单.md](交付核对清单.md)。
